## Result in one page

The request is `0x2001`, not the earlier guessed `0x1018`. It has four numeric
arguments:

```text
0x2001 [context, selector, mode, requested_track_count]
```

The modes are:

| Mode | Meaning | `selector` | Fourth argument |
| ---: | --- | --- | --- |
| `1` | Return child folders and banks | parent bank-list ID, or `0` for root | ignored in observed requests |
| `0` | Return tracks in one bank | bank-list ID | result count cap, floored to 3 |
| other | Unsupported | any | valid empty menu |

Mode 1 returns immediate children only. Folder nodes use item type `0x01`;
bank leaves use item type `0x2b`. Mode 0 returns ordinary 16-field track rows
whose argument 9 is the membership `TrackNo`. Unknown selectors, leaf IDs used
as parents, root used as a bank, empty banks, and unsupported modes all return a
normal zero-row menu rather than `0x4003` **[OBS]**.

The fourth argument affects only track mode. Values 0, 1, 2, and 3 each return
at most three rows; 4, 5, and 8 return exactly that many when available; 16
returned all ten resolvable memberships in the fixture. In server code this is
`max(requested_track_count, 3)` **[OBS, RB-DEC]**.

## Why `0x1018` was wrong

The original bounded tree walker derived `0x1018` by analogy with nearby root
categories. Rekordbox returned `0x4003` for `0x1018 [context, sort]`; that
capture remains useful as a rejected-route control. Root category ID `0x17`
and root item type `0x98` identify Hot Cue Bank in the browser tree, but neither
value determines the request kind arithmetically.

Three independent sources establish `0x2001`:

1. `DBCFmt_GetCmdPrmFmt` accepts `0x2001` with four numeric parameters
   **[RB-DEC]**.
2. `PSvDBMain::OnCueBnkCmd` dispatches `0x2001` through the master-database
   interface to `getHCBnkList` **[RB-DEC]**.
3. The XDJ-RR `dbcl_GetHotCueBank` wrapper passes `0x2001` to
   `dbcl_GetULong2`, and the browser handlers call that wrapper for root,
   folder, bank, reload, and drag/drop paths **[DEV-DEC]**.

The controlled fixture then returned populated folder and track menus for the
same request **[OBS, DB]**.

## Dispatch chain

The macOS 7.2.19 binary provides symbols and stable addresses for the relevant
server path:

| Address | Function | Role |
| --- | --- | --- |
| `0x101d2e730` | `PSvDBMain::OnCueBnkCmd` | Command-family dispatcher |
| `0x1016d1c60` | `PSvAppSyncDBIF::getHCBnkList` | Joined-SQL local-library implementation |
| `0x102524860` | `PSvMasterDBIF::getHCBnkList` | Serialized database-interface wrapper |
| `0x1004b2760` | `PSvDBMain::GetHCBnkList` | Alternate master-database list implementation |
| `0x1003f7eb0` | `DsqlHCBnk_GetRowContent` | Iterates tree nodes |
| `0x1003f8020` | `DsqlHCBnk_CloseRowset` | Closes the tree rowset |
| `0x100a05250` | `DsqlHCBnkSong_GetContentID` | Resolves ordered bank memberships |

For `0x2001`, `OnCueBnkCmd` extracts the selector, one-byte mode, and fourth
numeric argument from the parsed command and calls virtual slot `+0x270`.
The binary contains both `PSvAppSyncDBIF::getHCBnkList` and
`PSvMasterDBIF::getHCBnkList` implementations for that slot. The latter enters
the database critical section and calls `PSvDBMain::GetHCBnkList`; the observed
local-library count boundary matches the former **[OBS, RB-DEC]**.

The master-database `GetHCBnkList` clears list-buffer 1 before branching on the
mode byte. Mode 1 iterates `DsqlHCBnk_GetRowContent`. Mode 0 allocates three parallel arrays of
`max(fourth_argument, 3)` 32-bit entries, asks
`DsqlHCBnkSong_GetContentID` to fill content IDs and membership positions, then
resolves each positive content ID through `DsqlContent_GetSongInf`. Every path
inserts an end marker before returning its row count. The AppSync implementation
instead executes a joined SQL query and iterates its result under the signed
limit described below **[RB-DEC]**.

## Player call sites

The XDJ-RR decompilation supplies the client-side intent that the Rekordbox
binary alone cannot name:

- `chunk_0020.c:6465-6473`: `dbcl_GetHotCueBank` sends kind `0x2001` through
  the four-number helper `dbcl_GetULong2`.
- `chunk_0017.c:6356-6424`: `GetLeftHotCueBankList` requests selector 0 in
  folder mode for the root, then passes the selected row ID and row
  folder/leaf state on deeper navigation.
- `chunk_0017.c:8843-8872`: `GetRightHotCueBankList` performs the equivalent
  right-browser requests at menu location 2.
- `chunk_0021.c:3013-3022`: the reload path requests a bank's tracks at menu
  location 3 and consumes the ordinary left list buffer.
- `chunk_001f.c:6503-6549`: drag/drop requests a bank at menu location 7 and
  subsequently fetches Hot Cue Bank cue information.

The client therefore uses the same catalog request at several menu locations,
with different UI consumers. `dbcl_GetLeftBuf` sends the ordinary `0x3000`
render request with the same location byte and six numeric arguments:

```text
0x3000 [context, offset, limit, 0, header_total, 0]
```

The RX3 also accepts the established eight-argument form:

```text
0x3000 [context, offset, limit, 0, header_total, 12, 1, secondary]
```

Matching-location experiments at 1, 2, 3, and 7 accept both forms and return
the same three root rows. Render width does not alter location behavior. The
location itself selects a process-wide menu buffer, however, and that buffer
survives the TCP connection that populated it **[OBS]**.

The complete 4 x 4 x 2 cross-product ran in header-location order 1, 2, 3, 7.
Each `0x2001` request populated its own location before the render. The table
shows the repeated result for both six- and eight-argument renders:

| Header location | Render 1 | Render 2 | Render 3 | Render 7 |
| ---: | --- | --- | --- | --- |
| 1 | menu | timeout | timeout | timeout |
| 2 | menu | menu | timeout | timeout |
| 3 | menu | menu | menu | timeout |
| 7 | menu | menu | menu | menu |

This triangular shape is an initialization trace, not an ordinal permission
rule. At the start of each cold process, no location buffer exists. Rendering
an uninitialized location times out with `WouldBlock`. Once any query has
populated a location, later fresh TCP connections can render that location.
The earlier ten-case suite first populated all four matching locations and
then rendered location 3 after location-2 and location-7 headers; those
controls succeeded because location 3 already held its root rows **[OBS]**.

An ordered selector experiment proves the content is stale location state:

| New header request | Rendered location | Returned item IDs |
| --- | ---: | --- |
| location 1 root | 1 | `9002, 9001, 9003` |
| location 2 Beta Folder | 1 | `9002` from the old root buffer |
| location 2 Beta Folder | 2 | `9032` from the current Beta buffer |
| location 3 Alpha Folder | 2 | `9032` from the old Beta buffer |
| location 3 Alpha Folder | 3 | `9011, 9012, 9013` from the current Alpha buffer |
| location 7 Deep Folder | 3 | `9011` from the old Alpha buffer |
| location 7 Deep Folder | 7 | `9021` from the current Deep buffer |
| location 7 Beta Folder | 1 | `9002` from the original root buffer |

The new header total still determines the requested render window. A one-row
header therefore reads only the first row of a stale three-row buffer; a
three-row header aimed at a stale one-row buffer receives only that available
row. All three location experiments repeated after clean Rekordbox restarts,
left the process responsive, and added no Windows Application errors
**[OBS]**.

The device-disconnect path is narrower than a process restart. Static
`PSvDBMain::Disconnect` first clears the player's filter condition, then its
cached AIO classification, and finally calls `PSvDBComm::RequestToDrop`. It
does not directly call `DsqlListBuf_Clear`. Live evidence confirms the implied
boundary. A two-arm lifecycle experiment populated location 1, either retained
the identity or removed it for 40 seconds and rejoined, then issued a
location-2 Beta header while rendering old location 1. Both cold-process runs
in both arms returned item 9002 from the old location-1 root and item 9032 from
the current location-2 Beta buffer. The behavior signature is identical across
all four observations. Device disappearance and same-identity rejoin therefore
do not clear the context-keyed list rows **[OBS, RB-DEC]**.

The pinned macOS implementation explains the state boundary. `OnCueBnkCmd`
passes the complete packed request context to `getHCBnkList`. That function
uses it as the first argument to both `DsqlListBuf_Clear` and every
`DsqlListBuf_Insert`. The insert stores the value in column zero of the shared
`djmdLeftBuf` table. `GetListBufContents` supplies the render request's packed
context to `WhereListBuf_Condition`, which compares it for exact equality with
column zero. The code therefore keys rows by the complete context; the live
matrix proves that changing its location byte creates independently persistent
buffers across TCP connections **[OBS, DEC]**.

This result establishes wire compatibility, not UI equivalence: the XDJ-RR
still assigns locations 1, 2, 3, and 7 to left-browser, right-browser, reload,
and drag/drop workflows respectively **[DEV-DEC]**.

## Tree mode

Request:

```text
0x2001 [context, parent_id, 1, 0]
```

The root returned Beta Folder, Alpha Folder, and Root Bank in `Seq` order. The
Alpha Folder returned Alpha Bank, Deep Folder, and Empty Bank in `Seq` order.
The Beta Folder omitted its deleted leaf and returned Beta Bank. The Deep
Folder returned Deep Bank. Each bank leaf used as a parent returned an empty
menu **[OBS, DB]**.

Tree rows use this 16-field shape:

| Arg | Value |
| ---: | --- |
| 0 | `0` |
| 1 | `djmdHotCueBanklist.ID` |
| 2 | UTF-16 byte length of Name including NUL |
| 3 | `djmdHotCueBanklist.Name` |
| 4 | `2` |
| 5 | empty string |
| 6 | `0x01` for `Attribute=1`; `0x2b` otherwise |
| 7 | `0` |
| 8 | `0` |
| 9 | `djmdHotCueBanklist.Seq` |
| 10-12 | `0` |
| 13 | `2` |
| 14 | empty string |
| 15 | `0` |

Example folder and leaf rows are:

```text
[0,9001,26,"Alpha Folder",2,"",1,0,0,2,0,0,0,2,"",0]
[0,9003,20,"Root Bank",2,"",43,0,0,3,0,0,0,2,"",0]
```

Static construction agrees exactly: `GetHCBnkList` maps a true Attribute byte
to item type 1 and false to `0x2b`; it carries the returned ID, Name, and Seq
into the list-buffer record **[OBS, RB-DEC]**.

## Track mode and the fourth argument

Request:

```text
0x2001 [context, bank_id, 0, requested_track_count]
```

Alpha Bank produced these cardinalities:

| Fourth argument | Header total | Meaning |
| ---: | ---: | --- |
| 0 | 3 | floor to 3 |
| 1 | 3 | floor to 3 |
| 2 | 3 | floor to 3 |
| 3 | 3 | exact |
| 4 | 4 | exact cap |
| 5 | 5 | exact cap |
| 8 | 8 | exact cap |
| 16 | 10 | all resolvable memberships |
| 17 | 10 | all resolvable memberships |
| 255 | 10 | full 8-bit value, no narrowing |
| 256 | 10 | crosses 8-bit width |
| 65535 | 10 | full 16-bit value |
| 65536 | 10 | crosses 16-bit width |
| 1048576 | 10 | large positive count control |
| 2147483647 | 10 | maximum signed-positive count |
| 2147483648 | 0 | first signed-negative wire value |
| 4294967295 | 0 | maximum unsigned wire value (`-1` as signed) |

This is not pagination: the same prefix begins at the first membership each
time. It is the maximum number of membership slots resolved into the list
buffer, subject to the server's minimum count of three **[OBS, RB-DEC]**.

The six positive controls through 1,048,576 are byte-identical at the menu-row
level and repeat after a fixture reset and clean Rekordbox restart. Three
single-case cold-start probes establish the complete signed boundary:
`0x7fffffff` returns the same ten rows, while `0x80000000` and `0xffffffff`
return successful zero-row menus. Rekordbox remained alive and responsive in
all six executions, and each before/after Windows event-log window gained zero
application-error records **[OBS]**.

The active `PSvAppSyncDBIF::getHCBnkList` implementation explains both halves.
It queries all matching live content/membership rows, computes unsigned
`max(count, 3)`, stores the result as a 32-bit word, and stops its result loop
with signed `index >= limit`. Values through `INT32_MAX` therefore act as
positive caps; values with bit 31 set terminate before row zero. This path does
not allocate candidate arrays proportional to the request **[OBS, RB-DEC]**.

The separate `PSvDBMain::GetHCBnkList` implementation does allocate three
four-byte-per-candidate arrays before its legacy database query. Its presence
does not describe the observed local AppSync route and remains relevant only
to a client/database path shown to dispatch through that implementation
**[RB-DEC]**.

Track rows use the normal 16-field layout and current persisted secondary
column. In the captured Key configuration, Alpha Bank's first row was:

```text
[5002,10008,34,"Maximum Ordinary",4,"C",3844,0,
 10008,1,256,16,5002,4,"C",12350]
```

Argument 9 is the membership `TrackNo`, not `djmdContent.TrackNo`. The Root
Bank deliberately returned content 10002 at membership 1 before content 10001
at membership 2. Explicit duplicate memberships survive as separate rows:
content 10001 appears at positions 2 and 9. The locally deleted membership at
position 12 also survives. The membership's own `rb_local_deleted` flag is not
part of this serving predicate **[OBS, DB]**.

The membership to soft-deleted content and the dangling content ID did not
produce rows. The candidate membership sequence is therefore resolved through
the live content getter, and unresolved/non-live content collapses out of the
result **[OBS, RB-DEC]**.

The Deep Bank demonstrates signed ordering and unsigned rendering. Stored
`TrackNo=-1` precedes `TrackNo=0`, while the emitted 16-bit position is `65535`:

```text
content 10004 -> argument 9 = 65535
content 10003 -> argument 9 = 0
```

This distinction matters for implementations that sort after coercing the
value to an unsigned wire field **[OBS, DB]**.

### Large-bank render pagination

A separate 70-track bank (`ID 9070`) isolates catalog count from render
pagination. Request `2001 [context, 9070, 0, 70]` reports total 70. Complete
walks using one-row pages, automatic 32-row pages, and explicit windows
`[0,32]`, `[32,32]`, `[64,6]` all return content IDs 40001 through 40070 in
membership order **[OBS, DB]**.

Exact boundary windows preserve zero-based offsets: `[31,2]` returns
40032/40033 and `[63,2]` returns 40064/40065. Render count zero is normalized
to one row. Offsets at 70 and 71 both clamp to the final row. A request for ten
rows at offset 69 is right-aligned to IDs 40061 through 40070. Explicitly
overlapping windows repeat their shared row. Offset `0xffffffff` produces a
render timeout after the successful total-70 header **[OBS]**.

All 15 cases matched an immediate independent restart/repeat. The encrypted
fixture has database SHA-256
`1cc3c7eb27d4ca792b9fa7f6cf0c06e6cf9a7eb9b6b8727374b492e4b048c05e`
and logical fingerprint
`ec5330a568a242f8a85c5120cdada665d646be6ba7e70703f31b20d59b44c7a2`.
The declaration, golden, journal, hashes, and machine validation are retained
under `conformance/` and `data/experiments/hot-cue-bank/pagination/`. No media
files were present and backend comparison is deferred.

## Database semantics

The path uses:

- `djmdHotCueBanklist` for recursive folder/leaf nodes;
- `djmdSongHotCueBanklist` for bank-to-content membership and `TrackNo`;
- `djmdContent` plus its ordinary lookup tables for track rows;
- `djmdCue`, reached through membership `CueID`, for the master-database cue
  payload path;
- `hotCueBanklistCue`, used by adjacent synchronization/change paths rather
  than the observed `0x2001` catalog response.

Tree mode selects live rows whose `ParentID` matches the selector, ordered by
their persisted sequence. The controlled mixed fixture shows `Seq` governs the
wire order across folder and leaf types. Deleted nodes are excluded. Attribute
selects row class rather than causing recursive expansion **[OBS, DB, RB-DEC]**.

Track mode selects memberships for exactly one `HotCueBanklistID`, ordered by
signed `TrackNo`, limits the candidate array to the floored fourth argument,
and resolves each candidate through the ordinary content getter. Duplicate
membership is meaningful. The live-content resolution excludes deleted and
dangling content, while the observed membership flag itself is ignored
**[OBS, DB, RB-DEC]**.

A dedicated follow-up fixture supplies one live membership and cue beneath the
same soft-deleted bank. The parent tree still returns only live Beta Bank 9032,
proving `djmdHotCueBanklist.rb_local_deleted` hides the deleted node. Direct
requests by bank ID behave differently: catalog `0x2001` returns track 10005,
legacy cue request `0x2101` returns its one 36-byte record and extension, and
extended request `0x2301` returns its one 124-byte record. Bank deletion is
therefore a tree-navigation predicate, not a direct-ID authorization check;

## Cue-information request `0x2101`

The adjacent cue-information request has two numeric arguments:

```text
0x2101 [context, bank_id]
```

The Windows 7.2.19 command-format table defines two numeric fields for
`0x2101`. `SetHeader` supplies the packed context and
`dbcl_GetHotCueBankInfo` writes the bank ID into the second field.

argument 2 **[RB-DEC, DEV-DEC]**.

The active AppSync implementation can call

#### Duplicate-slot resolver anomaly

The successful fixture deliberately contains two active rows with the same
`HotCueBanklistID=9060` and `TrackNo=1`. Two disposable single-row controls
were tried first: one with a distinct membership ID and CueID, then one with
`CueID == ID`. Both returned exactly:

```text
4e02 [2401, 50, 0, empty_blob, 0]
```

Their immediate getters were unchanged and their stopped databases were
byte-identical to their fixtures. Aligning CueID was therefore insufficient.

`HCBnkSong_GetCueID` at `0x1016d2d70` explains the result. It executes the same
bank/slot query as the getter, calls `var::size()`, and branches to failure when
the result size is exactly one. Every other non-error size proceeds to index
row zero and read `CueID` and `ContentID`. The literal condition is:

```text
size == 1 -> failure
size != 1 -> read row 0
```

The extended setter then calls `SongHotCueBanklist.updateById` with that
resolved CueID. Two same-slot rows bypass the one-row rejection, and setting
each row's CueID equal to its own membership ID makes row zero the deterministic
update target. This looks like a Rekordbox AppSync implementation defect rather
than an intended database invariant **[OBS, DB, RB-DEC]**.

Slot 8 exposes the resolver's zero-row side of the same defect. The setter's
unsigned 16-bit gate at `0x1016d3fbd..0x1016d3fc9` admits exactly slots 1
through 8, but the mutation fixture has no bank-9060 membership at
`TrackNo=8`. `HCBnkSong_GetCueID` therefore proceeds to row zero with an empty
result. Across three independent cold processes, both the setter and the
immediate fresh-socket getter timed out while Rekordbox remained responsive,
the Application log remained clean, and the logical database remained
pristine. A same-database Rekordbox restart restored the canonical getter in
all three runs, returning status 0, one 124-byte baseline record, and identical
record hash `94bf967af4316fbeb78e3862ce09de2cfc57c616ed09ca882abd7c339b2589d0`.
This is a repeat-verified serving stall rather than a mutation or process exit;
attributing the stall specifically to the empty-result row access remains a
static/dynamic inference **[OBS, DB, RB-DEC]**.

### Seek-info behavior

`getUInt64Value` twice and `getUInt32Value` once parse unsigned decimal UTF-16
components, advancing past one non-digit separator. The 48-byte serialized
descriptor starts with little-endian `44`, followed by inbound/outbound 64-bit
pairs and 32-bit validity values in big-endian order **[RB-DEC]**.

The live edge behavior is hazardous and asymmetric:

- an outbound string alone is ignored because code jumps over outbound parsing
  when the inbound third component is zero;
- 74- and 81-byte setter records stop before the complete seek-option header;
  both return status zero, canonicalize to a 124-byte response, preserve empty
  seek strings, and keep the process responsive in two cold runs each;
- an 82-byte record ends immediately after the descriptor-length word `44`.
  Both cold runs time out after committing different nonempty inbound and
  outbound unsigned-decimal triplets assembled from storage beyond the
  supplied record, followed by the reply-path process fault and automatic
  replacement;
- lengths 121, 122, 123, and 124 return the same status-zero 124-byte record
  as the shorter safe controls and preserve empty strings;
- descriptor lengths 0, 1, 43, 44, 45, and `UINT32_MAX` do not alter the
  canonical 124-byte request result: all return status zero and empty strings;
- inbound validity zero and outbound-only validity return status zero and
  preserve empty strings;
- inbound validity one persists `1,3,1` inbound and `2,4,0` outbound, while
  inbound validity `UINT32_MAX` persists `1,3,4294967295` and `2,4,0`;
  both requests then time out with `WouldBlock` and overlap the faulting
  process with its automatic replacement in both cold runs **[OBS, DB]**.

The precise fault is an interior-pointer free in the AppSync getter. For a
nonempty `InPointSeekInfo`, the getter allocates and fills a UTF-16 buffer,
stores its base in a mutable cursor slot at `0x1016d363b`, and passes that slot
to two `getUInt64Value` calls and one `getUInt32Value` call. Every helper
advances the cursor past the parsed digits and separator. The getter then loads
the advanced cursor at `0x1016d3664` and passes it to `djrfree` at
`0x1016d366d`, rather than freeing the allocation base. Even a nonnumeric
nonempty string advances by one UTF-16 code unit before this free. The third
parse result also overwrites `r15d`, the register that previously held the
allocation base, so that base is unavailable at the free site **[RB-DEC]**.

The 82-byte result also proves that the option-region admission check does not
bound the subsequent fixed 44-byte descriptor copy by available request
storage. Its exact leaked numbers are process-dependent evidence and are not a
portable protocol value. The conformance summary retains those numbers but
normalizes only this variant to two three-component unsigned shapes when
checking repeat behavior; all other database fields remain exact-repeat
assertions **[OBS, DB, RB-DEC]**.

Process health is sampling-sensitive around the fault. The complete cold
matrix sampled two overlapping processes for every nonempty inbound case; an
earlier dedicated capture sampled the interval with no Rekordbox process. The
portable result is the timeout, durable database mutation, heap-fault path,
and automatic restart, rather than either instantaneous process count alone
**[OBS]**.

The outbound parser repeats the same sequence and interior free at
`0x1016d3813..0x1016d384b`. It is reached only after the inbound validity
component is nonzero; an outbound-only database string therefore remains
ignored, while the inbound allocation fault normally terminates the process
before outbound parsing. This static control flow exactly accounts for both
live outcomes. See `data/static-analysis/hot-cue-seek-fault.disasm.txt`
**[OBS, RB-DEC]**.

The crash cases remain under `data/experiments/hot-cue-bank/` and are excluded
from the routine golden suite. The strict seek summary covers 17 variants and
34 independent clean starts. No physical player was reachable, and no media
files were involved.
